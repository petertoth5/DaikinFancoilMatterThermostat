# Spike 002: esp-modbus 2.1.4 master on IDF v6.0.2 (esp32s3)

Status: **STOPPED at escalation S3** (user decision needed). No `mb_link` / `rs485_port` code is left in the tree; the evidence build used throw-away code that was removed.
Date: 2026-11-24. Input for `wiki-keeper`. No hardware was attached; nothing below claims on-board behaviour.

Path prefixes (source read only, nothing executed):
- `EM/` = `firmware/managed_components/espressif__esp-modbus/modbus/` (downloaded by the component manager from the registry, `==2.1.4`)
- `EMR/` = `firmware/managed_components/espressif__esp-modbus/` (repo root of the component)
- `IDF/` = `~/esp/esp-idf-v6.0.2/components/`

Method: source reading plus one throw-away image build in which a temporary `mb_link.c` called `mbc_master_create_serial`, `_start`, `_send_request` (FC03, qty 1), `_stop`, `_delete` and `app_main` called it (all reverted afterwards). The image build passed with the lint (`self-test: 82 cases ok`) and without compiler warnings.

## Result in one paragraph

**S3 escalation is hit.** `mbc_master_send_request` returns only an `esp_err_t`. A slave exception and a CRC/malformed reply both come back as `ESP_ERR_INVALID_RESPONSE`, and the exception code is not returned anywhere. Only the timeout is distinguishable (`ESP_ERR_TIMEOUT`). The three other hard-stop conditions did not trigger: S5 is as expected (RTS, low idle, high while transmitting), the library has no internal retries (S6), and no slave/TCP symbols are in the image (S12). Two further findings need the architect: `mbc_master_start` needs a descriptor table (`mbc_master_set_descriptor`), which the lint R1 list does not allow (see "Findings beyond S1-S12"), and the safe pin order for RTS is `uart_set_mode` first, then `uart_set_pin` (S5).

## S3 Error distinguishability (ESCALATION)

Call chain for a read: `mbc_master_send_request` -> `mbc_serial_master_send_request` -> `mbm_rq_read_holding_reg` -> `mb_port_event_wait_req_finish` -> `mb_err_enum_t` -> `MB_ERR_TO_ESP_ERR`.

| Case | How it arises (file:line) | `mb_err_enum_t` | `esp_err_t` returned to us |
|---|---|---|---|
| (a) timeout | respond timer fires, `mbm_rtu_transp_timer_expired` sets `EV_ERROR_RESPOND_TIMEOUT` (`EM/mb_transports/rtu/rtu_master.c:253-257`); `EV_ERROR_PROCESS` handler (`EM/mb_objects/mb_master.c:673-682`); also no event bits at all (`EM/mb_ports/common/port_event.c:214-216`) | `MB_ETIMEDOUT` (`port_event.c:195-200`) | `ESP_ERR_TIMEOUT` (`EMR/modbus/mb_controller/common/include/esp_modbus_common.h:91-93`) |
| (b) slave exception | frame OK, function byte has bit 7 set; `mbm_check_invoke_handler` returns early with the exception byte as `mb_exception_t` and does not call any handler (`mb_master.c:111-120`); `exception != MB_EX_NONE` -> `EV_ERROR_EXECUTE_FUNCTION` (`mb_master.c:648-650`) | `MB_EILLFUNC` (`port_event.c:207-212`) | `ESP_ERR_INVALID_RESPONSE` (`esp_modbus_common.h:97-99`) |
| (c) CRC / malformed | `mbm_rtu_transp_receive`: length < 4 or `mb_crc16 != 0` -> `MB_EIO` (`EM/mb_transports/rtu/rtu_master.c:161-179`); wrong address or wrong function code also set `EV_ERROR_RECEIVE_DATA` (`mb_master.c:606-623`) | `MB_ERECVDATA` (`port_event.c:201-206`) | `ESP_ERR_INVALID_RESPONSE` (`esp_modbus_common.h:100-102`) |
| (d) local error | `MB_EINVAL` (`mbfuncholding_master.c:271-273`), `MB_ENOREG` for address 0 (`:276-278`), `MB_EBUSY` (semaphore/resource, `:280-282`, `mbc_serial_master.c:165-275`) | `MB_EINVAL`, `MB_ENOREG`, `MB_EBUSY` | `ESP_ERR_INVALID_ARG`, `ESP_ERR_NOT_SUPPORTED`, `ESP_ERR_INVALID_STATE` (`esp_modbus_common.h:88-109`) |

Consequences:
1. (b) and (c) have the same return value (`ESP_ERR_INVALID_RESPONSE`).
2. The exception code (`buf[MB_PDU_DATA_OFF]`, `mb_master.c:118`) lives in a local variable `exception` in `mbm_poll` (`mb_master.c:646`) and is dropped; `mbm_error_cb_execute_function` only logs the **sent** frame at debug level (`mb_master.c:518-522`, `snd_frame`).
3. No side channel: the handler table cannot see exception frames (`mb_master.c:111-120` returns before the handler lookup at `:121-127`), `mbc_set_handler` only replaces handlers of normal function codes, and `mb_master_options_t` / `mbm_object_t` (private, `EM/mb_controller/common/mbc_master.h:49-59`, `mb_master.c:29-46`) hold no last-exception field. `mbc_master_send_request` also writes the same `ESP_LOGE` line for both (`esp_modbus_master.c:171-173`).
4. Worth knowing for the decision (not decided here): option E1 (classify by elapsed time) would give "reply before timeout, `exc_code = 0`" for both (b) and (c). The architecture rule D21 ("exception 02 -> register unsupported until reboot", "no retry on exception, 1 retry on timeout/CRC") needs exactly the (b)/(c) split plus the code, so E1 would lose the code 02 detection and the retry rule. Option E2 (own minimal RTU master over `rs485_port`) has no such limit. Both remain the user's decision.

## S4 Create/start/stop/delete transmit nothing
- The only transmit site in the serial master path is `uart_write_bytes` in `mb_port_ser_send_data` (`EM/mb_ports/serial/port_serial.c:334`). It is reached only via `frm_send` (`EM/mb_objects/mb_master.c:578`) on the event `EV_FRAME_TRANSMIT` (`mb_master.c:571`), which only the `mbm_rq_*` request functions post (`EM/mb_objects/functions/mbfuncholding_master.c:118,205,296,397` and the coil/discrete/input/other files, grep over `EM/` finds no other poster outside `mb_slave.c`). `mbc_master_send_request` is the only caller of `mbm_rq_*` we use.
- Create: `mb_port_ser_create` only calls `uart_param_config`, `uart_driver_install`, `uart_set_rx_timeout`, `uart_set_always_rx_timeout` and starts the port task disabled (`port_serial.c:242-263`); no `uart_set_pin`, no `uart_set_mode`. Start: `mbm_enable` -> `mbm_rtu_transp_start` -> enable port + timer and post `EV_READY` only (`rtu_master.c:120-130`, `mb_master.c:423-438`). Stop: `mbm_rtu_transp_stop` (`rtu_master.c:132-138`). Delete: `mbc_serial_master_delete` (`EM/mb_controller/serial/mbc_serial_master.c:96-131`) -> `mbm_delete` -> `mb_port_ser_delete` (`port_serial.c:285-293`).
- No break, no `uart_write_bytes_with_break`, no `uart_set_*` calls other than the ones listed (grep of `EM/` for `uart_set_mode|uart_set_pin|uart_tx_chars|uart_set_rts|uart_set_dtr|uart_set_line_inverse|uart_set_loop_back` returns nothing).
- Caveat that is IDF, not esp-modbus: once the TX pin is routed (`uart_set_pin`), the UART TX line idles high; DE stays low unless the half-duplex RTS rules in S5 raise it.

## S5 UART ownership, DE signal (expected result confirmed: RTS, low idle, high while transmitting)
- esp-modbus installs and deletes the UART driver itself: install `port_serial.c:242-249` (`uart_param_config` then `uart_driver_install(port, 256/260, 256/260, 20, &queue, ISR flag)`), delete `port_serial.c:289` via `ESP_ERROR_CHECK(uart_driver_delete(...))` (aborts if the delete fails). It never calls `uart_set_pin` or `uart_set_mode`; we must do that after create (`uart_set_mode` returns `ESP_ERR_INVALID_STATE` without a driver, `IDF/esp_driver_uart/src/uart.c:2164-2168`). Flow control is disabled by esp-modbus (`port_serial.c:233`), as `uart_set_mode` requires (`uart.c:2169-2172`).
- DE signal is **RTS** (esp32s3 half-duplex code only touches `sw_rts`, never DTR): `uart_ll_set_mode_rs485_half_duplex` sets `sw_rts = 1`, with the comment "sw_rts = 1 generates low level on RTS pin" (`IDF/esp_hal_uart/esp32s3/include/hal/uart_ll.h:773-783`, lines 775-776); `rs485tx_rx_en = 0`, `rs485rxby_tx_en = 1` (receiver off while transmitting, no echo), `rs485_en = 1`.
- Level while transmitting: `uart_enable_tx_write_fifo` sets `uart_hal_set_rts(.., 0)` before filling the TX FIFO in half-duplex mode (`uart.c:1190-1191`), i.e. `sw_rts = 0` = pin **high**; the TX_DONE ISR sets `uart_hal_set_rts(.., 1)` = pin **low** again after the last bit (`uart.c:1493-1506`). `uart_hal_set_rts` is `uart_ll_set_rts_active_level` (`IDF/esp_hal_uart/include/hal/uart_hal.h:137`, `uart_ll.h:679-682`).
- Pin routing: `uart_set_pin` routes the RTS signal with `gpio_matrix_output(rts_io_num, RTS_signal, false, false)` (`uart.c:958-960`), no inversion (`rts_inv` reset default 0, `IDF/soc/esp32s3/register/soc/uart_struct.h:589`).
- **Order (required)**: `sw_rts` resets to 0 (`uart_struct.h:517`), and the pin follows the inverse of `sw_rts` (see above), so a routed RTS pin in plain UART mode sits **high** (DE asserted). Therefore: (1) esp-modbus create (driver installed, no pin routed, DE GPIO still a plain output held low by `rs485_port`), (2) `uart_set_mode(RS485_HALF_DUPLEX)` (sets `sw_rts = 1`, pin value low once routed), (3) `uart_set_pin(tx, rx, de, NO_CHANGE)`, (4) `mbc_master_start`. Doing `uart_set_pin` before `uart_set_mode` would put DE high for the time in between. This conflicts with the order wording "uart_set_pin(tx, rx, de as RTS, NO_CHANGE), uart_set_mode(...)" in the interface comment of the spec, which therefore has to be read as mode-first.
- Delete: `uart_driver_delete` -> `uart_release_pin` -> `gpio_output_disable(rts)` (`uart.c:2116`, `:791-793`; `IDF/esp_driver_gpio/src/gpio.c:216-223`): DE floats (10 kOhm pull-down holds it low) until `rs485_port_release` drives the GPIO low again; it must re-drive after every delete.
- Silence check path: plain UART (`UART_MODE_UART`, pins `UART_PIN_NO_CHANGE` for TX/RTS/CTS) never routes the RTS signal; DE stays the plain GPIO output at 0 (the GPIO matrix default output is the GPIO register, `gpio_hal_matrix_out_default`, `gpio.c:225-228`).

## S6 Retries, timing, task priorities
- **No internal retry exists** in the serial master path: grep for `retr|attempt` in `EM/` outside TCP finds only `MB_SERIAL_RX_FLUSH_RETRY` (buffer flush loop, `port_serial.c:16,101`). `mbc_serial_master_send_request` makes exactly one `mbm_rq_*` call (`mbc_serial_master.c:186-272`). So "retries zero" holds with no option; the retry policy stays in `poll_sched`.
- Response timeout: `mb_serial_opts_t.response_tout_ms`; `mbc_serial_master_create` keeps it, or uses `CONFIG_FMB_MASTER_TIMEOUT_MS_RESPOND` (default 5000) if 0 (`mbc_serial_master.c:627-630`); `mbc_master_start` replaces values `0` or `>= CONFIG_FMB_MASTER_MAX_API_BLOCKING_TIME_MS` (6000) with the Kconfig value and logs a warning (`esp_modbus_master.c:209-220`); the transport applies it with `mb_port_timer_set_response_time` (`rtu_master.c:72-74`). So `response_tout_ms = CONFIG_DMT_BUS_RESP_TIMEOUT_MS` (range 200..2000, `main/Kconfig.projbuild:58`) works without any esp-modbus Kconfig change. The library minimum `MB_MASTER_MIN_TIMEOUT_MS_RESPOND` is 50 (`EM/mb_objects/include/mb_config.h:172`).
- Frame end / t3.5: reception ends on the UART RX timeout of 3 character times (`MB_SERIAL_TOUT = 3`, `port_serial.c:18,250`; frames of <= 3 bytes are dropped, `port_serial.c:169-173`, `MB_SER_PDU_SIZE_MIN = 3` at `EM/mb_ports/common/port_common.h:25`; a 5-byte exception frame passes). The t3.5 timer exists (`MB_RTU_GET_T35_VAL`, `EM/mb_transports/rtu/rtu_transport.h:34-41`: 7*220000/(2*9600) = 80 ticks of 50 us = 4.0 ms at 9600) but its expiry does nothing for the master (`rtu_master.c:248-252`, branch commented out). No inter-frame gap is enforced before sending a request except the cooldown below; our gap is `poll_sched`'s (>= 100 ms).
- Cooldown: after a respond-timeout, the next request waits until `CONFIG_FMB_MASTER_TIMEOUT_COOLDOWN_MS` (default 150) after the timeout (`EMR/Kconfig:132-139`, `mb_master.c:530-546,674-679`). It only lengthens the gap after a timeout; leave at default (no change in this task).
- Task priorities (defaults, to record, not changed): `CONFIG_FMB_PORT_TASK_PRIO = 10` -> `port_serial_task` priority 10 (`port_serial.c:262`), controller task `mbc_ser_master` priority 9 (`MB_CONTROLLER_PRIORITY = FMB_PORT_TASK_PRIO - 1`, `esp_modbus_common.h:43`, created `mbc_serial_master.c:570-576`); affinity `CONFIG_FMB_PORT_TASK_AFFINITY_CPU0` (core 0, `EMR/Kconfig:200-221`); stacks 4096 each (`FMB_PORT_TASK_STACK_SIZE`, `FMB_CONTROLLER_STACK_SIZE`, `EMR/Kconfig:157-164,266-272`); timer dispatch `ESP_TIMER_TASK` (ISR dispatch default n, `port_timer.c:65-69`, `Kconfig:282-291`). `bus_task` (priority about 10, core 1 per architecture) therefore shares priority 10 with `port_serial_task` but runs on the other core.
- No `sdkconfig.defaults` entry is needed for S6.

## S7 Addresses 0 and > 247
- `mbm_rq_read_holding_reg`: `snd_addr > MB_ADDRESS_MAX (247)` -> `MB_EINVAL` (`mbfuncholding_master.c:271-273`, `EM/mb_objects/include/mb_proto.h:18`); address 0 -> `MB_ENOREG` ("broadcast read not supported", `:275-278`), both before the resource take and before any transmit. The transport additionally rejects `slv_addr > 247` (`rtu_master.c:189-191`, `MB_MASTER_TOTAL_SLAVE_NUM`, `mb_config.h:173`). `mb_link_read` must still refuse 0 and > 247 itself (library behaviour is a second line of defence, not the guard).

## S8 FC03 qty 2..4
- `send_request` passes `reg_size` to `mbm_rq_read_holding_reg` and stores `data_ptr` as `reg_buffer_ptr` with `reg_buffer_size = reg_size` (`mbc_serial_master.c:172-173`, `:221-225`). The response callback `mbc_reg_holding_master_cb` copies `num_regs` registers into the buffer with a byte swap (`_XFER_2_WR`, `esp_modbus_common.h:73-76`; `esp_modbus_master.c:340-348`), requires `reg_buffer_size >= num_regs >= 1` (`:330`), so the caller buffer must hold `qty` `uint16_t` values, which come back in host order (big-endian wire values already swapped). No upper bound on `reg_size` is checked on the request side; our whitelist (qty 1..4, `daikin_regs_read_allowed`) is the guard. The byte-count check is `2 * reg_count == frame_ptr[byte_count]` (`mbfuncholding_master.c:321`); it does not compare against the received frame length (the frame is CRC-checked first and lives in a 260-byte buffer, so no overflow, only a theoretical stale-byte read for a CRC-valid but inconsistent frame).

## S9 Blocking semantics and thread safety
- `mbc_master_send_request` is blocking: it takes `mbm_sema` (up to `CONFIG_FMB_MASTER_MAX_API_BLOCKING_TIME_MS`, 6000 ms; `mbc_serial_master.c:165`), the request function takes the port resource (`mb_port_event_res_take`, `mbfuncholding_master.c:280-282`), then waits for the result bits (`mb_port_event_wait_req_finish`, `port_event.c:169-219`, max `MB_EVENT_QUEUE_TIMEOUT_MAX_MS` = 3000 ms, `port_common.h:28`). With a 500 ms response timeout it returns after the reply or the timeout plus frame time (CRC failures return immediately without waiting for the timeout: `mb_master.c:619-623`). The cooldown of S6 adds to the **next** call after a timeout.
- Thread safety: the semaphore serialises callers (`mbc_serial_master.c:165,276`); with one caller (`bus_task`) there is no contention. A small library quirk: if the semaphore take fails, the code still does `xSemaphoreGive` (`:273-276`) and returns `MB_EBUSY` -> `ESP_ERR_INVALID_STATE`; unreachable with one caller.
- `mbc_master_send_request` logs at error level on any non-OK result (`esp_modbus_master.c:171-173`); each timeout therefore produces a log line.

## S10 Delete releases UART and heap
- Source review: `mbc_serial_master_delete` stops if active, deletes the controller task, event group, semaphore (`mbc_serial_master.c:96-131`), then `mbm_delete` (`mb_master.c:391-421`: transport delete, handler unregister, `free(parent_name)`, `free(inst)`), which calls `mbm_rtu_transp_delete` (`rtu_master.c:107-118`: timer, event object, serial port, `free(transp)`), and `mb_port_ser_delete` (port task `vTaskDelete`, `uart_driver_delete`, semaphore, `free(port_obj)`, `port_serial.c:285-293`). The UART driver delete frees ring buffers, interrupt and releases the pins (`uart.c:2105-2142`). I found no allocation without a matching free on this path. Not proven: the heap numbers over repeated cycles and the abort in `ESP_ERROR_CHECK(uart_driver_delete)` if the driver cannot be deleted; both belong to the on-target check (008).
- The silence check -> init -> deinit -> silence check -> init sequence needs `rs485_port` to have no driver installed before create (`uart_driver_install` on an installed port fails, `port_serial.c:248-249`), as the spec precondition says.

## S11 Write handlers cannot be compiled out
- No Kconfig option removes them: the function enables are hard-coded `1` (`EM/mb_objects/include/mb_config.h:134-158`: FC03 and FC04, FC05/06/15/16/23 and coil functions); the Kconfig (`EMR/Kconfig:1-326`) has no `FMB_FUNC_*_ENABLED` entry (only RTU/ASCII/TCP mode and slave-ID options). Nothing to put in `sdkconfig.defaults` for S11.
- Write-capable symbols that are in the linked image (from `xtensa-esp32s3-elf-nm` of the evidence build, because `mbc_serial_master_send_request` switches over all function codes, `mbc_serial_master.c:186-272`, and `mbm_register_default_handlers` registers all response handlers, `mb_master.c:131-180`): `mbm_rq_write_holding_reg`, `mbm_rq_write_multi_holding_reg`, `mbm_rq_rw_multi_holding_reg`, `mbm_rq_write_coil`, `mbm_rq_write_multi_coils`, `mbm_fn_write_holding_reg`, `mbm_fn_write_multi_holding_reg`, `mbm_fn_rw_multi_holding_regs`, `mbm_fn_write_coil`, `mbm_fn_write_multi_coils`, plus `mbm_rq_custom`, `mbm_rq_report_slave_id`, `mbm_fn_report_slave_id`, `mbc_master_set_param_data`, and the parameter-set entries `mbc_serial_master_set_parameter(_with)` (vtable). They are reachable only through `mbc_master_send_request` with a non-0x03 `command` (or `mbc_master_set_parameter*`, which lint R1 forbids). The ELF check therefore cannot forbid these names; the guard stays lint R1/R8 on our source (command literally `0x03`). This is the "write capability exists in the library but is unreachable from our code" case of the spec; to be reported to the user.

## S12 No slave or TCP code in the image: OK, not hit
- All sources are compiled (`EMR/CMakeLists.txt:3-46` lists slave, TCP and ASCII files), but with a static library only referenced objects are linked. `nm` of the evidence image: no symbol matching `^mbc_slave_|^mbs_|^mbc_tcp_|mbm_tcp|mb_port_tcp|rtu_slave|ascii_slave` (command: `xtensa-esp32s3-elf-nm build/daikin_matter_thermostat.elf | grep -i "tcp_transp\|mbs_\|mbc_slave\|_slave\|mbm_tcp\|mbc_tcp\|mb_port_tcp\|mbm_port\|mbs_port\|rtu_slave\|ascii_slave"`). The only hits were Bluetooth ROM symbols (`hci_vs_*_pref_slave_*`, `ll_slave_*`, `r_lld_con_pref_slave_*`) and the *master-side* `mbm_rq_report_slave_id` / `mbm_fn_report_slave_id`. Lines matching `mbc_|mbs_` in the image: only `mbc_master_*`, `mbc_reg_*_master_cb`, `mbc_serial_master_*`, `mbc_ser_master_task` (list in the report).
- The ASCII master is linked (`mbm_ascii_*`) because `mbc_serial_master_create` references it when `CONFIG_FMB_COMM_MODE_ASCII_EN=y` (default, `EMR/Kconfig:109-113`, `mbc_serial_master.c:644-651`). It is not reachable with `mode = MB_RTU`. Disabling it is possible (`CONFIG_FMB_COMM_MODE_ASCII_EN=n`) but is an esp-modbus Kconfig change outside S6/S11, so it is not done; flagged as an option.

## Findings beyond S1-S12 (need architect attention)
1. **`mbc_master_start` requires a descriptor table.** `mbc_serial_master_start` returns `ESP_ERR_INVALID_ARG` unless `mbm_param_descriptor_size >= 1` (`EM/mb_controller/serial/mbc_serial_master.c:61-62`). That field is set only by `mbc_master_set_descriptor` (`:151`) and is **uninitialised** after `mbc_serial_master_controller_create` (`malloc` without `memset`, `:554`; no other assignment in `EM/` outside the TCP file). So start is nondeterministic without the call. `send_request` itself does not read the table. Needs a one-entry table (`cid = 0`, non-NULL `param_key`, `mb_size > 0`; checks at `:141-149`), and the call `mbc_master_set_descriptor`, which is **not** in lint R1's allowed list (`firmware/tools/check_bus_access.py:30-36`, check at `:85`) nor in the task spec's list. `tools/check_bus_access.py` is owned by 001, not by task 002. Either the lint allowed list gains `mbc_master_set_descriptor` (a spec change) or an alternative must be found. Not worked around here.
2. **Pin order** in the spec interface comment for `rs485_port_attach` ("uart_set_pin ..., uart_set_mode ...; order per S5") must be mode first (S5).
3. Because of the uninitialised-field problem and the exception/CRC merge, a decision between E1 and E2 should also consider the amount of private library behaviour we would depend on (descriptor table workaround, `ESP_ERROR_CHECK` in delete, cooldown).
