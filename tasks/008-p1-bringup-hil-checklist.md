## Content requirements

### A. Safety (first page, tick boxes, before any wiring step)
1. Fancoil and wall panel are mains powered. Open housings, connect or disconnect wires and do resistance/continuity measurements **only with mains off**, following the appliance manual.
2. **Never touch the "+ A B -" block** (panel <-> fancoil) **and never the CP terminal** of the "A A B B -" block: do not loosen, measure on or reconnect them. Only one A, one B and "-" of "A A B B -" are used.
3. Node GND to "-" **only after** C.4 showed "-", A and B within -7..+12 V of node GND (architecture section 4, RS485 common-mode range, external). The node runs on normal USB power (user decision 2026-11-09). Note: whether the panel's low-voltage side is isolated from mains is not stated in the wiki (architecture section 8).
4. Live voltage readings (C.4) only on the low-voltage terminals with mains parts covered; if that is not possible, skip them, leave node GND unconnected and say so in the log.
5. **Abort** (unexpected panel/fancoil behaviour, error code, icon, smell, heat): type `mb poll off`, unplug the node's USB power (DE then held low by the 10 kOhm pull-down / MAX485 unpowered), mains off before touching any wire. Record what happened. Unplugging USB alone also stops all transmission.
6. **The node transmits on its own.** With a clean boot silence check, polling starts automatically and the first frame goes out about 5 s after power-up (006, user decision 2026-11-09). Therefore: connect or disconnect A/B only with the node unpowered (and mains off, A.1); open the serial console before powering the node while it is wired, ready to type `mb poll off`. A `mb poll off` typed within the first 5 s prevents the first frame (006); later it stops polling after the current transaction.

### B. Bench (before going on site)
1. Wiring per architecture section 4: TX GPIO -> DI; RO -> level shift/divider -> RX GPIO (RO is a 5 V output unless U1 is a 3.3 V part, `entities/max485`); DE and /RE tied -> DE GPIO with 10 kOhm to GND (Q1, D8). Record the GPIOs; they must equal `CONFIG_DMT_BUS_TX_GPIO` / `RX_GPIO` / `DE_GPIO` (defaults 5/4/6 are placeholders). Record U1 marking and module supply.
2. Unpowered module: A-B resistance; DE-/RE continuity; DE-GND = 10 kOhm.
3. Flash the phase-1 image; record the git commit, the `fw=` value of the first console line `# dmt-probe v1 addr=<a> baud=<b> fw=<version>` (006 boot sequence), and that `build-verifier` reported lint and ELF check passed.
4. Node powered, bus not connected. Console output formats (006, `txn_log` v1 of 010): `T <t_start_ms> <dur_ms> <addr> <kind> <reg> <qty> <result> [values | exception code]` with result `OK`, `TIMEOUT`, `EXC`, `BADFRAME` or `ERROR`; `H <t_ms> <health>`. While the 5 s check runs, `mb status` shows `boot silence: <ms> ms, activity running`. After about 5 s: `# silence ok, polling on: mb poll off to stop` and `H <t> ONLINE` (automatic start), then `H <t> DEGRADED` and, at the 5th consecutive failure, `H <t> OFFLINE` (no slave). `mb status` then shows `boot silence: <ms> ms, activity 0` and `write: compiled out`. Then `mb poll off` (`H <t> STOPPED`) and measure the DE pin **low** (multimeter). Without a slave every `T` line must be `TIMEOUT`, never `BADFRAME`, and `mb status` must show `link counters: gap_bytes 0 ...` and `faults since boot: 0`: a `BADFRAME` here means bytes were received during or after our own transmission (RX line floating while /RE is high, 014 "RX line while transmitting"); record and stop, back to the architect (amended 2026-11-24, user decision E2). If activity > 0 with A/B open, the receiver sees an unbiased floating line (bias resistors on the module unverified; this risk note user-approved 2026-11-09): record and stop; this goes back to the architect, not to a relaxed firmware setting.
5. Abort-path check: reboot and type `mb poll off` within the first 5 s: `mb stats` shows `txns 0` and `mb status` shows `health: STOPPED` (A.6). Then `mb probe` (no slave): all `T ... SWEEP ... TIMEOUT`, `mb status` health stays STOPPED. `mb silence 5` five times, each time waiting for its result line (B.12): each run prints `# silence check: started 5 s` and then `# silence check 5s ok, polling off: mb poll on to start`, no `# mb_link: ... failed` line, and `faults since boot` in `mb status` does not change (UART driver delete/re-install cycle of 014; spike S10; amended 2026-11-24). Free heap: the 006 image prints no heap figure (`mb status` has no heap line), so heap stability over the five cycles is recorded as "not checked (no heap output in the 006 image)" (amended 2026-11-24, user decision: accepted for phase 1, no change to 006). DE pin low again afterwards. Note: the activity value in `mb status` is the **boot** check's value; the result of a `mb silence` run is only in its result line.
6. DE timing (amended 2026-11-24, user decision: 014 review; amended 2026-11-24, user decisions Q-HW1 and Q-HW2). There is no oscilloscope and no logic analyser on the bench or on site (Q-HW1). The following 014-review checks **cannot be decided in phase 1**; record each one as **"not measured (no instrument, Q-HW1)"**: DE low at boot without a glitch; no glitch when the port opens (`uart_set_pin`, after the silence check); rising edge before the first start bit of each request; falling edge within about 100 us after the last stop bit (TX_DONE ISR release, 014); worst-case DE-fall delay; no DE pulse during `mb silence 5` and during the close that precedes it. DE with concurrent flash/NVS activity (014 M2): record **"not done in phase 1, repeat at phase-2 bring-up (Q-HW2)"**; the 006 image has no command to create flash/NVS load and none is added. Record the following indirect evidence; it does **not** replace the measurement and none of it turns the items above into a pass:
   a. Static DE level (multimeter, DC, DE pin to node GND): low during the 5 s boot window, after `mb poll off` (B.4, B.5) and after each `mb silence 5` (B.5). A multimeter shows a level averaged over time; it cannot show a glitch or an edge time.
   b. Averaged DE level while `mb probe` runs without a slave (multimeter, DC; bench only): expected close to 0 V, because DE is high only while the 8-byte request is sent (about 8 ms at 9600, external) and transactions are at least 100 ms apart (architecture section 3, D16), so the high share is a few percent at most (inferred). A reading close to the 3.3 V GPIO level means DE stays high after the request: **hard stop**, record and stop, back to the architect (amended 2026-11-24, user decision).
   c. On site (D.8): DE and /RE are tied, so while DE is high the receiver output is high-impedance (014 "RX line while transmitting", `entities/max485`); a complete `OK` reply therefore implies that DE was high for the whole request and fell before the reply's first byte arrived (inferred). The D.8 `OK`, `TIMEOUT` and `BADFRAME` counts of `mb stats`, `gap_bytes` and `faults since boot` are the per-transaction indirect evidence. They do not bound the fall delay.
   d. No console evidence exists for a glitch at boot, at port open, or during the close and `mb silence`; these stay undecided (residual risk, architecture section 8).
7. No slave connected, RX pull-up on (amended 2026-11-24, user decision: 014 review; extends B.4): every `T` line is `TIMEOUT`, never `BADFRAME`; `gap_bytes 0`. A `BADFRAME` means the RX line still picks up garbage while /RE is high despite the pull-up (014 "RX line while transmitting"): record and stop, back to the architect.
8. Ports (amended 2026-11-24, user decision: 006 review): record which console is used, UART0 or USB-Serial-JTAG, and that the bus is on UART1 (`mb status` first line `bus: uart 1`; `CONFIG_DMT_BUS_UART_PORT` default 1). Any other combination: stop, back to the architect.
9. No uart INFO line (amended 2026-11-24, user decision: 006 review): in the saved boot output and after each `mb silence`, the IDF line containing "queue free spaces" does **not** appear (006 sets the `uart` log level to WARN). If it appears: record it, not a stop condition.
10. `bus_task` stack (amended 2026-11-24, user decision: 006 review): `mb status` "bus_task stack high-water (minimum free)" once after boot (after the first `H` line) and once after one `mb silence 1`; both values >= about 1 KB (1024 bytes). Less: record and stop, back to the architect.
11. Abort path evidence (amended 2026-11-24, user decision: 006 review; extends B.5): after `mb poll off` in the 5 s window the saved output has **no `T` line** at all before the next command, and after the window the lines `# silence ok, polling off: mb poll on to start` and `H <t> STOPPED`; `mb status` typed during and after the window shows `addr: kconfig <k> current <a>` with `<a>` not 0 and `health: STOPPED` (during the window also `boot silence: <ms> ms, activity running`), and `mb stats` shows `txns 0` (006 rule M2, snapshot published before the silence check).
12. `mb silence N` pacing (amended 2026-11-24, user decision: 006 review): while `mb silence N` runs the node executes no command; wait N s (until its result line) before typing more commands. The command queue holds 8 entries; extra commands are refused with `command not queued: ESP_ERR_TIMEOUT`.
13. Pending read cancelled by `mb silence` (amended 2026-11-24, user decision: 006 review): reboot and, within the 5 s boot window, type `mb read 000 1` then `mb silence 1`. Expected: no `T ... MANUAL 000` line at all (the read was cancelled); `# silence check: started 1 s`, then the silence result line `# silence check 1s ok, polling off: mb poll on to start`, then the boot hint `# silence ok, polling off: mb poll on to start` and `H <t> STOPPED`; polling off. A `MANUAL` line after the silence result: record and stop, back to the architect.
14. Latched run (amended 2026-11-24, user decision: 006 review; bench only, never on site; only if a second RS485 or USB-UART adapter is at hand to put bytes on A/B or the RX side during the 5 s boot window, otherwise "not done"): expected lines `# silence check: started 5 s`, `# silence check: activity <n>, latched until reboot`, `# latched until reboot: no transmission`, `H <t> LATCHED`; no `T` line; `mb status` shows `health: LATCHED` and `boot silence: <ms> ms, activity <n>` with n > 0; `mb poll on`, `mb probe` and `mb silence` are refused with `# mb poll on refused: latched until reboot`, `# mb probe refused: latched or a sweep is running` and `# mb silence refused: latched, reboot only`; DE pin low. Reboot without the adapter afterwards.
15. Port fault (amended 2026-11-24, user decision: 006 review; informational, only if one occurs): exactly one line `# mb_link: port fault, link closed (mb silence or reboot to recover)`; `mb status` shows `faults since boot` and `link closed: ...` until a passed `mb silence`, after which `link closed` disappears and `faults since boot` keeps its value.

### C. On site, mains off, node not connected
1. Photo of both terminal blocks before any change.
2. Continuity A-A and B-B of the doubled terminals (item 11); choose one A and one B.
3. Resistance A-B at the panel port (item 11; termination rule of architecture section 4: about 120 Ohm -> fit the user's 120 Ohm at the node end; high/open -> start without and judge by the error rate of item 7). Resistance "-" to the CP terminal (shared "-"?, item 11; measure without touching the CP wiring).
4. Mains on, node powered but not wired to the panel: with the meter between node GND and each panel terminal, DC voltage of "-", A, B; then A-B at the panel. Mains off.
5. Confirm the panel address on the panel itself (item 1): standby, hold AUTO 5 s, read the value, wait 10 s without changing anything (`concepts/device-addressing`, p6). Record it. If it differs from the image's address, use `mb addr <n>` in D.3 (never scan).

### D. Connect and probe
1. Mains off, node unpowered: connect node A/B (and GND to "-" only if A.3 allows) with short leads, no star; fit 120 Ohm only if C.3 says so. Mains on.
2. Open the serial console and start saving the complete serial output, then power the node. Boot silence check runs 5 s; afterwards `mb status` must show `boot silence: <ms> ms, activity 0` (item 3). **If activity > 0 the node latches and will not transmit** (lines `# silence check: activity <n>, latched until reboot`, `# latched until reboot: no transmission`, `H <t> LATCHED`): do not reboot to retry; abort and record (foreign traffic or an unbiased line; both go to the architect). With activity 0 polling starts by itself (`# silence ok, polling on: mb poll off to stop`, `H <t> ONLINE`, A.6): watch the panel from the first frame (item 9). If C.5 gave an address other than the image's, type `mb poll off` within the 5 s window, then `mb addr <n>` and `mb poll on` (if the window was missed: `mb addr <n>` at once).
3. Logging is on from power-up (006), so the saved output holds every `T` line from the first frame; type `mb log off` only if the console is too noisy to work in (then `mb log on` before D.7). `mb probe`, then `mb regs` (items 1, 2, 4).
4. If nothing answers: `mb poll off`, unplug the node, mains off, swap A/B on the node side only, mains on, repeat D.2-D.3 (item 2). Still nothing: `mb poll off`, stop and report.
5. Multi-register test: `mb read 200 4`, `mb read 000 2`, `mb read 242 4` (item 5).
6. Polling has run since D.2 (`mb poll on` only if it was stopped). Watch the panel display for anything new, e.g. a WEB icon (item 9, `concepts/web-restriction-flags` flag 0).
7. Keypress correlation with logging on (default; `mb log on` only if it was switched off in D.3), each action with wall-clock time: setpoint up, setpoint down (231 vs 008), each fan mode (201 bits 0-2 order), season change (233 values 3/5), standby on/off (201 bit 7) (item 8).
8. Soak >= 1 h of polling; `mb stats` at 1, 10, 60 min: `txns` >= 1000, `latency ms (answered): min / median / max` (item 6), `error rate (timeout+bad_frame+error)/txns` < 1 %, `offline entries 0`; panel normal: display, icons, error codes, local keys (item 7). Note for item 6: the logged duration (`dur_ms` of the `T` lines, and the `mb stats` latency) is the whole transaction (8-byte request, about 8 ms at 9600, plus the slave's reply time plus the end-of-frame silence wait of 10-20 ms with the default tick, 014), not the slave's pure response time; the pure response time is not measured (D.8b).
8a. Slave inter-byte timing (amended 2026-11-24, user decision; recorded with items 6 and 7, no new exit item): at 1, 10 and 60 min also note from `mb status` `max_byte_interval_us` and `gap_bytes` (line `link counters: ...`) and `faults since boot`. One character lasts about 1042 us at 9600 8N1 (external); an interval well above about 2600 us (one character plus t1.5, external, approximate) means the answering slave pauses inside its replies. The node tolerates that (014 end-of-frame rule: silence never ends a frame before its expected length) but records it; `gap_bytes` > 0 means bytes arrived between transactions (late replies or foreign traffic). Resolution is limited by task wake-up latency (inferred, tens of us). Which device answers on "A A B B -" is the panel per the wiki (inferred, `entities/ekwhctrl1`); record what is observed, do not conclude more. If any `BADFRAME` lines appear, note their times next to these values. Counter limits (014 M3, amended 2026-11-24, user decision: 014 review): `gap_bytes` is a lower bound (bytes dropped by the driver are not counted) and `max_byte_interval_us` is approximate (time-stamped when the task reads the byte, so it includes wake-up latency); state this next to the recorded values.
8b. Slave turnaround (amended 2026-11-24, user decision: 014 review; amended 2026-11-24, user decision Q-HW1; amended 2026-11-24, user decision: item 6, replaces 008-b "measure the slave turnaround on site"): pure turnaround **"unknown, no instrument (Q-HW1)"**: the time from the end of our request to the first reply start bit, and the cross-check of `max_byte_interval_us` against the longest inter-byte gap of a real reply, both need a scope or logic analyser. Consequence: `max_byte_interval_us` stays unconfirmed and approximate (014 M3). Indirect evidence to record (derived, not a measurement): from the saved `T` lines, the minimum and maximum `dur_ms` of `OK` lines with qty 1. A qty-1 transaction contains the 8-byte request (about 8.3 ms), the turnaround, the 7-byte reply (about 7.3 ms; one character about 1042 us at 9600 8N1, reply length per the Modbus spec, external) and the end-of-frame wait of at least 10 ms (014 rule 4), plus task latency, so the turnaround is **at most about `dur_ms` - 25 ms** (inferred, approximate, 1 ms timestamp resolution). Log it always as "upper bound, derived, not measured", never as a measured turnaround.
8c. Known limit, no action (amended 2026-11-24, user decision: 014 review; 014 rule 4; amended 2026-11-24, user decision Q-HW1): with the default 100 Hz tick every transaction ends with a 10-20 ms end-of-frame wait, so the logged transaction time in D.8 is longer than the slave's turnaround. Accepted; record the transaction times and the derived upper bound from D.8b; do not treat the difference as a fault.
9. `mb poll off` for > 300 s (e.g. 10 min): watch panel and fancoil; `mb poll on`; `mb regs` for 105 bit 0 and, if readable, 104 bit 12 (item 10, `concepts/flag-registers`).
10. `mb silence 60` with the panel connected; wait 60 s for the result line (B.12). Expected `# silence check 60s ok, polling off: mb poll on to start`, i.e. activity 0 (item 3, panel is a slave, inferred). Activity is shown as `# silence check: activity <n>, latched until reboot`; judge by these lines, not by `mb status` (its `boot silence` line keeps the boot check's value). Polling stays off afterwards (006).
11. `mb poll off`, unplug the node, mains off, disconnect the node, photo, mains on; confirm panel and fancoil work as before and that "+ A B -" was untouched.

5. Plain language, numbered steps, tick boxes, no emojis.
